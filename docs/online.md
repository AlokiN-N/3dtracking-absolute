# Покадровый трекер жёстких объектов

Трекер возвращает `Frame;Loc_X;Loc_Y;Loc_Z` в мировой системе камер. Единица CSV — сантиметр. Положение относится к опорной точке выбранной модели. Для прежней команды Way1 по умолчанию используется CargoTruck с опорной точкой на переднем нижнем крае кабины. Поддерживаются синхронные видео с неподвижными и движущимися калиброванными камерами.

## Запуск

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
bash tools/get_yolo26.sh
bash tools/get_sam2_tiny.sh

mkdir -p data
tar xf ~/Downloads/project2.7z -C data
.venv/bin/python -m online.run --data data --out out/way1 --sam models/sam2/sam2.1_hiera_tiny --threads 5 --video
.venv/bin/python -m online.evaluate --out out/way1 --reference data/object_transform_SM_AA_track.csv
ffmpeg -i out/way1/control-raw.mp4 -c:v libx264 -crf 22 -pix_fmt yuv420p -movflags +faststart out/way1/control.mp4
.venv/bin/python -m online.serve --out out/way1 --port 18765 --reference data/object_transform_SM_AA_track.csv
```

На входе ожидаются файлы `object_transform_CineCameraActor<N>.csv` и по одному MP4 с именем, оканчивающимся на `CineCameraActor<N>.mp4`. Нумерация кадров начинается с 0. Для кадра с пропуском калибровки используется информация остальных камер. Состав CSV камер, размеры матрицы и соглашения UE наследуются от `core`. На проверочном наборе без эталона достаточно запуска `online.run`.

Новый экспорт с `Focal_Length_mm` и `matrix_size.txt` принимается напрямую через `--data`. Фокусное применяется покадрово, а FFmpeg сопоставляет временные метки видео с общей сеткой кадров калибровки. Общая частота должна быть постоянной, а ноль PTS должен соответствовать нулю калибровки. Пропуск в одном потоке не сдвигает остальные. Старые выгрузки по умолчанию используют порядковые номера. Режим можно явно задать через `--sync pts` или `--sync index`.

На Debian использован `onnxruntime-gpu[cuda,cudnn]` вместо CPU-пакета `onnxruntime`. В журнале запуска перечисляются активные провайдеры YOLO и SAM.

`trajectory.csv` пополняется по одному кадру и сбрасывается на диск после каждого результата. Пустые координаты означают потерю. `replay.json` сохраняет камеры и режим на каждом кадре. `--limit N` позволяет проверять префикс роликов. Без `--sam` остаются YOLO26 и оптический поток. Этот режим требует меньше вычислений и может пропускать маленькую цель.

Для сцен с ложными захватами доступен `--global-seg /path/to/yolo26l-seg.pt`. Ultralytics ищет объект по всему кадру каждой камеры. Для верхних ракурсов при недостатке наблюдений дополнительно проверяются повёрнутые фрагменты. В многокамерной сцене первый и повторный захват требуют разнесённых лучей и совпадения силуэта CAD со свежими масками минимум двух камер. После захвата трекер может продолжить по одной камере, кратко перенести маску оптическим потоком или выдать прогноз до одной секунды. Для запуска требуются PyTorch, Ultralytics и локальный чекпойнт сегментации.

В этом режиме `--sam-video facebook/sam2.1-hiera-base-plus` сохраняет 2D-сопровождение после пропуска YOLO. SAM2 получает последнюю принятую маску и кадр этой же камеры, затем обрабатывает кадры по порядку до 2,5 секунды после свежего наблюдения. Проверенные 2D-маски отмечены `TRACKED 2D` на видео и записаны в `tracked_2d_boxes`. Если основной трекер перестал выдавать координаты, две сопровождаемые маски могут восстановить 3D-позу. Трекер проверяет разнос и согласованность лучей, совпадение CAD с обеими масками и смещение от недавней позы. Слабое совпадение в одном ракурсе допустимо при сильном совпадении во втором. Если переход от предыдущей выданной позиции слишком резкий, на границе остаётся пропуск. Восстановленные кадры получают статус `mask_multi` с пустым полем скорости. Для SAM2 Video требуются Transformers, PyTorch и чекпойнт модели. Также доступен облегчённый вариант `facebook/sam2.1-hiera-tiny`.

После истечения горизонта 3D локальное 2D-сопровождение может продолжаться, пока совпадающая детекция подтверждает непрерывную маску хотя бы раз в 1,5 секунды. Эти маски отображаются как `TRACKED 2D LOCAL`, камеры перечислены в `local_2d_cams`. Они не участвуют в восстановлении 3D.

При `--sam-video-fallback facebook/sam2.1-hiera-large` резервная модель запускается при двух последовательных пропусках 3D у основной ветки. Она обрабатывает сохранённую историю от последней принятой детекции до текущего кадра в пределах 2,5 секунды. Для статуса `mask_large` нужны согласованные маски в двух ракурсах, совпадение позы с оценкой по маскам Base Plus или прогнозом движения и плавный переход от последней выданной позиции. Резервная оценка хранится отдельно от состояния основной ветки.

`--cad-points` продолжает 3D по видимым точкам метрической CAD-модели, если основной трекер перестал выдавать позу. Подтверждённая двумя ракурсами поза привязывает точки изображения к видимой поверхности. Трекер переносит их с предыдущего кадра, отбрасывает точки вне текущей маски и проверяет позу по точкам, которые не участвовали в подгонке. Нужен треугольный `--target` либо `--appearance-target` с теми же единицами, осями и началом координат. Результат получает статус `cad_points` и оценку локальной неопределённости `cad_reference_std_m` в метрах.

При добавлении `--gotrack-source PATH --gotrack-checkpoint PATH` пропуск можно восстановить по соответствиям между текущим изображением и видимой поверхностью рендера CAD. Для выдачи нужны согласованные решения на двух последовательных кадрах. Поза проверяется при обработке второго кадра и относится к нему.

`--cad-regions` добавляет два способа продолжить трек после подтверждённой позы. Статус `cad_flow` означает, что перенос видимой поверхности подтверждён прямым и обратным плотным оптическим потоком и репроекцией. Статус `cad_region` означает, что перенос подтверждён видимой частью силуэта. Проекция обрезается по границе камеры, а проверка нескольких близких ориентаций отсеивает неоднозначную глубину. Оба метода используют текущий кадр и историю, результаты основной ветки имеют приоритет.

Траектория содержит `Speed_m_s` и `Speed_km_h` после трёх координат. Это оценка модуля 3D-скорости центра CAD по текущим и недавним наблюдениям. После пропуска, прогноза, оценки только по оптическому потоку или скачка окно набирается заново. Пустое поле означает, что измерений для скорости пока недостаточно.

## Другая модель и камеры

Создайте `target.json` рядом с моделью. Масштаб переводит единицы CAD в метры, а `origin` задаёт измеряемую точку в исходных координатах CAD. По умолчанию это начало координат файла. Для геометрии, измеренной в миллиметрах, укажите `0.001`. Поддерживаются GLB, OBJ, PLY и STL. Для FBX нужен `assimp` в `PATH` или путь к нему в `PELENG_ASSIMP`. На Debian Assimp доступен в пакете `assimp-utils`.

```json
{
  "name": "Inspection probe",
  "mesh": "probe.glb",
  "meters_per_unit": 1.0,
  "origin": [0.43, -0.18, 0.22],
  "max_speed_mps": 5
}
```

Если есть только вершины, вместо `mesh` можно передать `parts`, массив наборов XYZ для выпуклых частей. Универсальный режим оценивает три угла и перемещение по всем осям. Он использует выпуклые оболочки отдельных частей CAD для сопоставления силуэтов. Допущение о движении по поверхности включается явно через `"level_surface": true`. При наличии известного класса детектора можно указать `labels`. Для незнакомого класса или нескольких похожих объектов передайте начальную рамку и используйте SAM. Рамка задаётся в пикселях исходного кадра. Для уверенной метрической инициализации полезно дать её в двух разных ракурсах. Симметричная модель может иметь несколько поворотов, которые дают одинаковую проекцию.

```bash
.venv/bin/python -m online.run --cameras cameras.json --target target.json --out out/probe \
  --sam models/sam2/sam2.1_hiera_tiny --seed-box 3:261,205,381,289 \
  --seed-box 9:183,215,309,288 --video
```

В `cameras.json` укажите запись для каждой камеры. Пути отсчитываются от каталога манифеста, имена видео произвольны. `intrinsics_px` задаёт `[fx, fy, cx, cy]` для фактического разрешения видео. Положение камеры читается из CSV в порядке `Frame;Loc_X;Loc_Y;Loc_Z;Rot_Roll;Rot_Pitch;Rot_Yaw`, углы задаются в градусах в соглашениях Unreal. При другом формате калибровки сначала преобразуйте позы к этим соглашениям. Видеопотоки должны быть синхронизированы и исправлены от дисторсии.

```json
{
  "location_meters_per_unit": 0.01,
  "cameras": [
    {"id": 3, "video": "stream_a.mp4", "poses": "cal_3.csv", "intrinsics_px": [545, 527, 315, 237]},
    {"id": 9, "video": "stream_b.mp4", "poses": "cal_9.csv", "intrinsics_px": [554, 536, 318, 237]}
  ]
}
```

Если камеры уже лежат в исходном формате Unreal, можно использовать прежний `--data` вместе с `--target`. Для новой модели `replay.json` также сохраняет `yaw_pitch_roll_deg`. Данные об эталонном положении нужны только отдельной команде оценки.

### Уточнение позы по полной CAD-модели

PicoPose можно включить для любой модели с треугольной сеткой. Он сопоставляет пиксели текущего кадра с 3D-точками отрендеренных шаблонов. Робастное решение PnP подгоняет позу на части точек и проверяет ошибку на остальных. Поправка принимается, когда два шаблона дают близкие позы, крупный ракурс лучше согласуется с проекцией и дополнительные ракурсы не дают сопоставимого углового разрешения. Поправка применяется к текущему выводу. Следующий шаг трекера сохраняет своё независимое состояние.

Для этого режима нужны CUDA, PyTorch с поддержкой GPU, torchvision, `mmcv-lite`, `omegaconf` и `einops`. Используйте официальный [исходный код и чекпойнт PicoPose](https://github.com/foollh/PicoPose). На Linux проверен исходник `543f8fe0dc8fe014a602113977fc034bd9b4578d` с PyTorch 2.11 CUDA 12.8 и `mmcv-lite` 2.2. Добавьте к команде:

```bash
--pico-source /path/to/PicoPose --pico-checkpoint /path/to/picopose.ckpt
```

При запуске с готовым профилем силуэтов Way1 передайте полную сетку отдельно через `--appearance-target`. Её масштаб, оси и опорная точка должны совпадать с профилем. Поле `axes` переставляет оси исходного CAD после вычитания `origin`. Например, `[2, 0, 1]` задаёт порядок Z, X, Y. При запуске с полным CAD в `--target` этот же файл используется для обоих методов.

Параметр `--joint-pose` с включённым PicoPose добавляет совместную подгонку одной 3D-позы по соответствиям между точками CAD и пикселями текущего кадра в нескольких камерах. Режим проверяет разнос лучей и принимает поправку, если она согласуется с масками и уменьшает ошибку на отложенных точках в каждом участвующем ракурсе. При недостатке пригодных соответствий действует обычная оценка. Метод использует геометрию заданного CAD и калибровки камер. Для смены объекта достаточно заменить манифест модели и при необходимости указать её начальные рамки.

В прежней версии совместной подгонки 45 кадров Way1 ухудшились относительно базового PicoPose. Два самых больших ухудшения пришлись на резервные оценки по движению. В текущем варианте они исключены из многокамерной поправки. Поза также должна совпасть при раздельной подгонке по двум группам точек. Это устранило 24 из прежних 45 ухудшений без новых. В сравнении с базовым PicoPose MSE составила 9,76 вместо 10,01 м², MAE — 2,51 вместо 2,57 м. Параметр `--joint-motion-check` дополнительно требует, чтобы смещение центра CAD подтверждалось оптическим потоком минимум двух камер между соседними кадрами.

При повторной проверке на исходных кадрах Way1 с сохранёнными кандидатами многокамерной подгонки `--joint-motion-check` исключил все 45 прежних ухудшений. Он сохранил три многокамерные поправки. Вместе с переносом однокамерной глубины это дало десять улучшений, MSE 9,90 м² и MAE 2,54 м без покадровых ухудшений. Это результат повторной проверки кандидатов, а опубликованный результат получен полным прогоном с `--mono-depth`.

Параметр `--mono-depth` переносит глубину на короткий участок с одной камерой. Недавние согласованные многокамерные оценки дают положение и скорость, а текущая камера задаёт луч. Поправка меняет дальность вдоль этого луча, если проекция CAD согласуется с силуэтом и измеренным движением. Подтверждённая оценка глубины по текущему кадру имеет приоритет перед переносом. Для смены модели используются её собственный метрический размер и ограничение скорости. Дополнительная задержка выдачи равна нулю.

На полном Way1 `--mono-depth` улучшил семь из 384 однокамерных оценок без покадровых ухудшений. MAE по однокамерным кадрам снизилась с 3,05 до 3,00 м, число кадров с ошибкой менее метра выросло с 54 до 60. На всех кадрах с эталоном MSE снизилась с 10,01 до 9,92 м², MAE — с 2,57 до 2,55 м. Максимум остался 9,65 м. Первые 112 результатов совпали с отдельным коротким прогоном. На синтетическом приборе с другой CAD-моделью после отключения двух камер трекер сохранил координаты и ошибку менее метра на всех 32 кадрах теста.

Параметр `--guard-flow-jumps` проверяет резкие скачки, когда все выбранные маски перенесены оптическим потоком. Если две предыдущие оценки согласуются с ограничением `max_speed_mps` модели, трекер проверяет короткий прогноз по силуэту камеры, наблюдавшей объект все три кадра. Поправка применяется к координатам текущего кадра. В `replay.json` она отмечается полем `flow_jump_guard`.

Экспериментальный параметр `--joint-spatial-check` вместе с `--joint-pose` разделяет соответствия для подгонки и проверки по областям изображения. Он оценивает неопределённость позиции по ошибкам проекции, исключая из этой оценки априорную позу. Дополнительные ракурсы с надёжной маской могут отклонить поправку.

Параметр `--recover-second-view` проверяет дополнительные маски, если трекер принял только одну камеру. PicoPose сопоставляет пиксели с текущей CAD-моделью. Поправку проверяют по отдельным областям каждого изображения и по движению между кадрами `t−1` и `t` в обеих камерах. При принятии поправки `replay.json` записывает добавленную камеру в поле `recovered_camera`. Для этого режима нужна треугольная CAD-модель и PicoPose.

На полном Way1 второй ракурс принят на кадре 512. Ошибка кадра снизилась с 3,4585 до 0,2854 м. Покрытие составило 1001 из 1001, ни одна из 999 оценок с эталоном не ухудшилась. Отдельный прогон первых 540 кадров совпал с полным прогоном. Режим включён в опубликованной версии.

Экспериментальный параметр `--surface-pose` привязывает пиксельные точки к видимой треугольной сетке после надёжной оценки по нескольким камерам. При следующем кадре трекер сопровождает точки оптическим потоком и уточняет только параметры позы, которые поддерживают изображения. Режим работает с треугольным `--target` или `--appearance-target` и может использоваться без PicoPose. Поле `surface_cams` перечисляет камеры, поддержавшие принятую поправку. Обе экспериментальные опции работают при `k=0`.

## Как вычисляется оценка

1. Для камеры с постоянным центром совмещаем изображение `t−2` с текущим по известному повороту, затем выделяем компоненты движения. При переносе камеры опираемся на сегментацию текущего кадра и оптический поток. YOLO26 даёт первый захват и повторную детекцию. SAM 2.1 уточняет маску по области движения, KLT переносит её между вызовами модели с проверкой туда и обратно.
2. Весовое пересечение лучей даёт старт для подгонки. SciPy минимизирует устойчивую ошибку между масками и проекциями геометрии FBX, дополнительно совмещая видимые рёбра кузова с границами на изображении. Если камеры расходятся, решатель повторяет подгонку без наблюдения с худшим перекрытием. Когда направление движения хорошо различимо, сравниваем проекцию курса с оптическим потоком и проверяем гипотезу разворота на 180°.
3. С одной камерой глубину оцениваем по размеру модели. Для дальних наблюдений дополнительно учитываем высоту из предыдущих надёжных оценок. При крупном изображении грузовика ориентируемся на масштаб силуэта и рёбра, чтобы оценивать высоту при движении по склону.
4. При потере маски используются рёбра в области движения, подтверждённый оптический поток или ограниченный по времени прогноз. В интерфейсе эти режимы видны отдельно.

Скорость оценивается по центру модели, а выходная точка остаётся на кабине. Это снижает влияние неоднозначного разворота модели на прогноз перемещения. При согласовании ракурсов проверяется полнота дальних масок. Фильтр выходной позы осторожно принимает большие поправки глубины от одной камеры и подтверждает разворот модели курсом в нескольких кадрах.

Фильтр учитывает, что при одном ракурсе дальность определена слабее, чем направление на цель. Крупные поправки принимаются быстрее при подтверждении из двух независимых ракурсов. На крупном боковом изображении дополнительно подгоняются прямые рёбра кузова. Эта проверка корректирует дальность вдоль луча камеры. Резкая смена высоты, замеченная только в одном ракурсе, не обновляет опорную высоту.

Для ровного участка сохраняется высота кабины из недавних кадров, в которых её видят несколько камер. Оптический поток между соседними кадрами переносит подтверждённую точку кабины по плоскости этой высоты. При потере ракурса поправка используется только при согласованном движении и достаточном совпадении с текущим силуэтом.

Если исходная поза помещает опорную часть объекта за пределы маски, проверяется её видимость в позе, предложенной оптическим потоком. У края кадра также проверяется поправка вдоль луча камеры. Для неё учитывается совпадение в видимой области изображения и согласие с накопленным движением. Опорные вершины и смещение центра передаются из геометрии модели.

При резком скачке вдоль луча дальность проверяется ещё раз. Трекер переносит недавнюю позу, подтверждённую рёбрами или высотой дороги, на текущий луч по оптическому потоку. Для близкого объекта поправка требует согласия с текущей подгонкой силуэта или лучшего совпадения с крупным силуэтом при слабых дополнительных ракурсах. При потере одного из ракурсов ранее подтверждённая оценка может сохраниться, если оба ракурса независимо подтверждают перенос. Переносятся только координаты и признаки качества. Для оптического потока нужны изображения двух соседних кадров.

Каждый вызов трекера получает один синхронный набор изображений. В памяти на камеру два последних кадра. Из более ранней истории передаётся состояние трекера. Эталон открывается отдельной командой после прогона.

Покадровый режим означает вычисление без будущих кадров. Частота вычислений зависит от оборудования и количества камер. Веб-плеер воспроизводит результат с частотой исходных роликов.

## Устойчивость к сбоям камер и наблюдений

Режим `online.run --robust` добавляет проверки перед 3D-оценкой. Он остаётся причинным. Для оценки дрожания используются текущий и предыдущий кадры, а для поиска движения доступно окно до двух предыдущих кадров.

| Событие | Что делает трекер |
| --- | --- |
| Перепад освещения | Сравнивает яркость с недавними кадрами камеры. При резком перепаде нормализует экспозицию. Для поиска движения отдельно компенсирует разницу яркости между кадрами. Плоский чёрный или пересвеченный кадр исключается. |
| Тени и перекрытие объекта | Проверяет, где маска находится относительно ожидаемой проекции, и перепроверяет согласие ракурсов при подгонке модели. Резкая смена курса допустима при подтверждении изображениями. При полном перекрытии возможен краткий прогноз. |
| Дрожание камеры | Учитывает записанный поворот камеры. Небольшой остаточный поворот оценивает по фоновым точкам вне объекта. Поправка применяется к лучам 3D-подгонки, когда совпадения распределены по кадру и ошибка проекции заметно уменьшается. Для сильного поступательного дрожания нужны актуальные внешние параметры камеры, например от визуальной одометрии с IMU. |
| Камера выключилась или вернулась | Пропускает кадр без изображения или калибровки и продолжает с доступными камерами. При возврате начинает новую историю изображения этой камеры. Интерфейс `Tracker.step` принимает набор синхронных кадров и калибровок для каждого шага. Состав камер может меняться по их ID. |
| Выброс или пропуск детекции | Отбрасывает далёкие маски и не переносит отвергнутую маску в следующий кадр. Большой скачок 3D-позиции требует согласия ракурсов с достаточным углом между лучами. При пропуске использует проверенный оптический поток или прогноз. После двух секунд без пригодного сигнала отмечает потерю трека. |

Результат `--robust` сохраняет `available_cams` и `camera_health` по кадрам. Статусы `forecast` и `lost` отделяют прогноз и потерю от наблюдения. При отключении камеры точность зависит от того, какие ракурсы остались. Подключение устройств, синхронизация и доставка кадров выполняются до вызова `Tracker.step`.

Вариант `--adaptive` проверяет камеры на каждом кадре, а строгие ограничения подгонки включает при подтверждённом перепаде экспозиции, коррекции дрожания, пропуске камеры или непригодном кадре. Защита остаётся активной ещё примерно 0,2 с после последнего сбоя. Поле `guard_active` отмечает эти кадры. В обычном кадре используются штатные правила отбора наблюдений. `--adaptive` и `--robust` выбираются по отдельности. Любой из них можно сочетать с `--joint-pose`.

На полном Way1 без внесённых помех все 1001 координаты в режиме `--adaptive` совпали с опубликованными. На 180 кадрах со смешанными сбоями MAE составила 2,86 м против 4,32 м в штатном режиме и 2,44 м при постоянной защите. В отдельном интервале отключения камеры №1 `--adaptive` дал 4,50 м против 4,34 м в штатном режиме и 0,60 м при постоянной защите. Для отключений важно измерять качество на конкретной расстановке камер.

На 64 синтетических кадрах с одновременным дрожанием, перепадами света, перекрытием, ложными масками и отключениями камер MAE снизилась с 3,08 до 0,24 м, максимальная ошибка — с 6,89 до 0,64 м. При дрожании движущейся камеры MAE снизилась с 0,084 до 0,048 м. Отдельный тест с резкой сменой курса дал максимум 0,54 м. Эти тесты моделируют перечисленные возмущения. Субметровую точность на исходном Way1 они не подтверждают.

На первых 180 кадрах Way1 с внесёнными сбоями и без PicoPose MAE снизилась с 4,32 до 2,44 м, RMSE — с 5,67 до 3,39 м. В отдельном тесте с отключением камеры №1 MAE на интервале отключения снизилась с 4,34 до 0,60 м. На интервале чёрных кадров камеры №2 она выросла с 0,97 до 1,21 м. На полном исходном Way1 с PicoPose опубликованный режим даёт MAE 2,57 м и RMSE 3,16 м. Режим защиты даёт MAE 3,00 м и RMSE 4,37 м, поэтому доступен отдельно через `--robust`. Кадров с ошибкой меньше метра 258 из 999 в опубликованном режиме и 310 из 999 в режиме защиты.

Дополнительный режим `online.run --lag 5` записывает `trajectory-lag.csv` сразу после выдачи каждой сглаженной точки. Положение кадра `t` оценивается локальной линейной подгонкой по готовым 3D-координатам в окне `t−k…t+k`. В начале окна используются доступные кадры. Точка выдаётся на кадре `t+k`, указанном в столбце `Available_At_Frame`. Последние `k` кадров записи остаются в ожидании продолжения потока.

Для уже сохранённого прогона та же команда сглаживания строит оранжевую траекторию и считает метрики на общей части с причинным режимом. Значение `--lag` задаётся в кадрах.

```bash
.venv/bin/python -m online.smooth --out out/way1 --lag 5 --reference data/object_transform_SM_AA_track.csv
```

На Way1 при `k=5` выдано 996 точек из 1001. На 994 общих кадрах с эталоном MSE составила 8,23 вместо 10,05 м², MAE — 2,35 вместо 2,57 м, максимальная ошибка — 7,46 вместо 9,65 м.

В веб-демо над графиком можно изменить задержку `k`, число предыдущих кадров и метод. В симметричном окне число предыдущих кадров равно `k`. Отключите этот переключатель, чтобы задать историю независимо. При `k=0` сглаживание использует только доступные к текущему моменту координаты. Демо пересчитывает траекторию, метрики и файлы выгрузки при изменении полей. Для воспроизведения этих настроек из командной строки используйте `--lag`, `--history` и `--method linear|mean` в `online.run` или `online.smooth`.

## Оценка и публикация

`online.evaluate` считает MSE как среднее `dx² + dy² + dz²` в м², а MAE как среднее 3D-расстояние до эталона в метрах. Команда сохраняет покадровые ошибки, метрики и график «эталон / оценка». Доля выданных координат и доля зрительных наблюдений считаются отдельно. В Way1 два поля эталона, в кадрах 402 и 691, записаны датами. Эти кадры и строка 1001, выходящая за конец видеоряда, исключаются из оценки по эталону. Покрытие считается по всем 1001 кадрам.

После оценки обоих прогонов `python -m online.compare --before out/baseline/replay.json --after out/candidate/replay.json` проверяет каждую ошибку, сохранение координат на всех ранее покрытых кадрах и снижение MSE, MAE и максимальной ошибки. PicoPose улучшил 42 из 999 кадров с эталоном. Остальные 957 дали ту же ошибку. На кадре 756 ошибка уменьшилась с 9,81 до 0,68 м. Максимум 9,65 м приходится на кадр 952. На последних 51 кадре MSE составила 12,88 м², а MAE 3,20 м. Отдельный запуск первых 842 кадров дал те же координаты, камеры, режим и уверенность, что и полный прогон.

Числа для e03 и e04 взяты из исходной ветки. Их MSE получен из опубликованного RMSE. У офлайн-варианта есть глобальное сглаживание и доступ к будущим кадрам. Для проверки смены CAD использован синтетический прибор, который вращается по трём осям и меняет высоту. На трёх камерах с разными калибровками трекер выдал все 64 координаты со средней ошибкой 0,051 м и максимальной 0,199 м. Первые 37 кадров совпали с отдельным коротким прогоном. Качество на реальном видео с другим объектом ещё предстоит проверить.

Защита от скачков улучшила кадры 917 и 952 без ухудшений на остальных размеченных кадрах. На последних 51 кадре MSE снизилась с 12,88 до 11,27 м², MAE — с 3,20 до 3,08 м, максимальная ошибка — с 9,65 до 5,79 м. В Linux-демо используются `--mono-depth` и `--guard-flow-jumps`.

Сервер отдаёт статический повтор, графики и координаты, рассчитанные трекером. Демоверсия работает на Debian под отдельной службой `peleng-hackathon-demo.service`. HTTPS на порту 8443 проксирует только демосервер на loopback-порту 18765. [Открыть демо](https://plane.tail6ffd57.ts.net:8443/).
